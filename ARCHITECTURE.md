# ARCHITECTURE.md — верхнеуровневая карта системы

> Топ-уровневая карта доменов и слоёв прототипа APM ГлоуБайт. Держим её короткой
> и актуальной. Детали продукта — в `docs/product/main.md`, стек — в
> `docs/techstack/main.md`.

## Текущая стадия

Реализация. Создан каркас (React 19 + TS + Vite) и сквозной срез — Реестр активов.
Выполнена **фаза 0 обвязки**: доменная модель и Zod-схемы по всем сущностям v1,
наполненные сиды демо-предприятия, переключаемые режимы хранения (in-memory /
localStorage / IndexedDB через Dexie) со сбросом к сидам и интерактивный CRUD
(RHF + Zod) в Реестре. Выполнена **фаза 1**: Поиск активов (фильтры по полям и
атрибутам классов + сохраняемые представления), Справочники (классификатор с
атрибутами + CRUD опорных сущностей), Статусные схемы (конструктор состояний и
переходов; смена статуса актива уважает схему). Выполнена **фаза 1.1** (техдолг
фазы 1): статус актива хранится как ссылка `Asset.statusId` на состояние схемы
`ss-asset` (не enum), владелец/планировщик — ссылки `ownerId`→`OrgUnit` и
`plannerId`→`Person`; смена статуса и тон бейджа идут от состояния схемы через
`services/status-flow.ts` (`resolveAssetStatus`). Записи старого формата в
localStorage/Dexie мигрируются на чтении адаптером `data/migrations.ts`
(подключён через `migrate` в `EntityDescriptor`). Маршруты грузятся лениво
(`React.lazy` + общий `Suspense` в `AppShell`), вендоры разнесены по чанкам
(`build.rolldownOptions.output.codeSplitting`). Выполнена **фаза 1.2** (проработка
карточки активов): имя актива в реестре и поиске — ссылка на полную карточку по
маршруту `/assets/:assetId` под `AppShell` (`AssetCardPage`, lazy), новая вкладка —
только по команде из контекстного меню (`shared/ui/ContextMenu`); под реестром —
краткая панель `AssetPreviewCard` по выбранной строке; полная карточка показывает
виджеты связанных сущностей (стратегия/мероприятия, обходы, критичность, дефекты)
через селекторы `services/asset-related.ts`, форматирование атрибутов вынесено в
`features/asset-registry/assetView.ts`. Выполнена **фаза 2** (APM-надстройка):
Анализ критичности (матрица 5×5 + ранжирование, `services/criticality.ts`),
Стратегии и мероприятия (CRUD стратегий и задач ТОиР, привязка к активам/классам,
расписание через `date-fns`, рекомендации по критичности — `services/strategies.ts`)
и Обходы и маршруты (конструктор маршрутов, выполнение обхода с вводом замеров,
журнал; замер вне диапазона порождает дефект/уведомление — `services/rounds.ts`).
Вкладки карточки актива «Стратегия и мероприятия» и «Обходы и замеры» наполнены
данными (тренды замеров — Recharts). Начата **фаза 3**: выполнен **план 10**
(симулятор телеметрии) — чистая логика генерации показаний в `services/telemetry.ts`,
императивный контроллер таймера в `store/simulatorStore.ts`; отклонение датчика
порождает дефект/уведомление общей фабрикой с обходами. Симулятор управляется из
системных настроек (старт/стоп/скорость), а уведомления видны через индикатор в
верхней панели оболочки (`app/NotificationsMenu.tsx`). Следующие шаги фазы 3 —
дашборд надёжности (план 11) и роли (план 12). Разделы Дашборд и Роли пока заглушки.
Планы: `docs/exec-plans/active/skeleton-scaffold.md` и
`docs/exec-plans/active/feature-buildout/` (дорожная карта обвязки).

## Общая концепция

Прототип — это веб-приложение (EAM + APM), которое **симулирует** работу системы
управления надёжностью активов. Реальных интеграций нет: внешние данные
(телеметрия оборудования, SCADA/IoT, ERP) имитируются предзаполненными данными и
генератором показаний.

## Домены (бизнес-области)

Соответствуют разделам продукта (см. `docs/product/main.md`):

- **Реестр активов** — иерархия функциональных мест и оборудования, карточка актива.
- **Поиск активов** — фильтры и сохраняемые представления.
- **Стратегии и мероприятия** — стратегии обслуживания и задачи ТОиР.
- **Обходы и маршруты** — маршруты, выполнение обходов, замеры.
- **Анализ критичности** — оценка критичности оборудования.
- **Статусные схемы** — настраиваемые состояния и переходы.
- **Справочники** — классификаторы, оргструктура, производители и т.д.
- **Дашборд** — сводные KPI надёжности.

## Целевые слои (предполагаемое разделение)

Планируемое направление зависимостей — «вперёд» по слоям (уточняется в `techstack`):

```
Типы/Модель  →  Данные (моки/сиды)  →  Сервисы/логика  →  UI (экраны)
                                  ↑
                  Симуляторы (телеметрия, "интеграции")
```

Слой сервисов появился в фазе 1: `src/services/` содержит доменную логику,
переиспользуемую разделами (напр. `status-flow.ts` — применение статусных схем,
расчёт разрешённых переходов и контекст статуса актива `resolveAssetStatus`;
`asset-related.ts` — селекторы связанных сущностей для виджетов карточки актива:
мероприятия, обходы/замеры, критичность, дефекты). Фаза 2 добавила:
`criticality.ts` (риск-балл и класс по матрице, рекомендация типа стратегии),
`strategies.ts` (выбор задач стратегии, расписание ТОиР через `date-fns`, сводка
рекомендаций по критичности) и `rounds.ts` (валидация замера по допустимому
диапазону, тренды и фабрики дефекта/уведомления из отклонения — общий механизм с
симулятором телеметрии). Фаза 3 добавила `telemetry.ts` — чистая логика генерации
показаний датчиков во времени (случайное блуждание около предыдущего значения,
периодический выход за диапазон); побочные эффекты (таймер, запись через
репозиторий) вынесены в `store/simulatorStore.ts`, а не в сервис.

Миграции данных живут на границе хранилища: `data/migrations.ts` описывает
адаптеры «сырой записи» (напр. `migrateAsset`), которые подключаются к датасету
через поле `migrate` в `EntityDescriptor` и применяются всеми репозиториями на
чтении перед Zod-валидацией. Так старые персистентные записи переводятся в новый
формат без связывания обобщённого репозитория со спецификой сущности.

Принцип: строгие границы между слоями, зависимости направлены в одну сторону.
Конкретные технологии и структура папок фиксируются в `docs/techstack/main.md`.

## Симуляция вместо интеграций

Любая «интеграция» — это локальный симулятор внутри репозитория:
- предзаполненные данные демо-предприятия (металлургия/обогащение);
- генератор показаний во времени, который периодически выдаёт отклонения;
- отклонение на обходе → порождает дефект/уведомление.
