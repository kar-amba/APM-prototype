# Дорожная карта: конфигуратор матриц риска

- Статус: active
- Дата: 2026-06-08

## Назначение

Расширить прототип APM ГлоуБайт **настраиваемой подсистемой матриц риска**.
Сейчас в продукте есть единственная **жёстко зашитая** матрица критичности 5×5
(`src/services/criticality.ts`, `src/model/criticality.ts`): фиксированные оси
1…5, фиксированное произведение `consequence × probability` и фиксированные пороги
классов (low/medium/high/critical). Целевой вид — это конфигурируемая система, в
которой инженер по надёжности сам настраивает матрицы, шкалы, категории
последствий и цветовые зоны под конкретный вид анализа.

Эта дорожная карта покрывает требования:

1. **Несколько матриц риска под разные виды анализа** — ACA, FMECA, RCM, RBI и
   управление стратегиями. Для каждого вида анализа может быть одна или несколько
   матриц, одна из них — по умолчанию.
2. **Настройка шкал** — вероятности, последствий, критичности и ранга риска
   (число уровней, подписи, описания, числовые «якоря»).
3. **Настройка категорий последствий** — производство, безопасность, экология,
   качество, финансы (плюс возможность добавить свои), с описанием каждого уровня
   тяжести по категории.
4. **Настройка уровней риска и цветовых зон** — именованные уровни (напр.
   низкий/средний/высокий/критический/экстремальный), цвет/тон зоны и **пороги
   перехода** между зонами по риск-баллу (или явная окраска ячеек).

Это **индекс**: он задаёт цель, целевую модель данных, фазы и зависимости.
Конкретная работа вынесена в отдельные лёгкие планы в этой директории — по одному
на рабочий блок. Каждый план самодостаточен, чтобы его можно было взять в
отдельной сессии агента.

## Контекст и принципы

- **Слои не нарушаем:** `Модель → Данные → Сервисы → UI` (см.
  [`../../../../ARCHITECTURE.md`](../../../../ARCHITECTURE.md)).
- **Границы данных — через Zod:** новые сущности описываем схемами в `src/model`.
- **Доступ к данным — только через репозиторий** (`src/data/repository.ts`), UI не
  знает о хранилище; новые датасеты регистрируем в `src/data/datasets.ts` и сидируем
  в `src/data/mock`.
- **Единый визуальный язык** — дизайн-система
  [`../../../brandbook-template.html`](../../../brandbook-template.html); цветовые
  зоны строим на семантических токенах (`--color-success/info/warning/error`) и
  переиспользуем обёртки `src/shared/ui` (Badge, Tabs, Modal, Card).
- **Все строки — через i18n** (`src/shared/i18n`, ключи `riskConfig.*`).
- **Конфигурация — редактируемый агрегат:** в отличие от плоских сущностей
  статусной схемы (`Status`/`Transition`), дочерние коллекции конфигурации
  (уровни шкалы, уровни риска, описания категорий) **встраиваем массивами в
  родительский документ** — он редактируется и валидируется как единое целое.
  Это сознательное упрощение для конфигуратора (см. журнал решений).
- **Совместимость:** существующий `CriticalityAssessment` и раздел «Анализ
  критичности» должны продолжать работать; переход на конфигурируемую матрицу
  делаем через сид матрицы ACA 5×5, воспроизводящей текущие пороги, + миграцию.
- **Симуляция, не интеграции** (core-belief №5): никаких внешних источников;
  справочники видов анализа и стандартные шкалы — предзаполненные сиды.

## Что такое виды анализа (для агента без отраслевого контекста)

- **ACA** (Asset Criticality Analysis) — ранжирование оборудования по критичности;
  текущая матрица критичности — это частный случай ACA.
- **FMECA** (Failure Mode, Effects & Criticality Analysis) — анализ видов и
  последствий отказов; критичность вида отказа по матрице «последствия ×
  вероятность/возникновение».
- **RCM** (Reliability-Centered Maintenance) — выбор стратегии обслуживания на
  основе последствий отказа.
- **RBI** (Risk-Based Inspection) — риск-ориентированный контроль (чаще для
  статичного оборудования: сосуды, трубопроводы); матрица «вероятность отказа ×
  последствия», часто **с явной окраской ячеек**, а не строго произведением.
- **Управление стратегиями** — матрица, по которой класс риска подсказывает тип
  стратегии ТОиР (реактивная → ППР → по состоянию → предиктивная).

## Целевая модель данных (v1)

Три новых корневых сущности (новые ключи `AppRepository`), дочерние коллекции
встроены массивами:

```
RiskScale                       // шкала: набор упорядоченных уровней
├─ id, code, name
├─ kind: probability | consequence | criticality | rank
├─ description?
└─ levels: RiskScaleLevel[]     // { order(1..N), code, label, description?, anchor? }
                                //   anchor — текстовый «якорь» уровня
                                //   (напр. «1 раз в 10 лет», «> 10 млн ₽»)

ConsequenceCategory             // категория последствий
├─ id, code (production|safety|ecology|quality|finance|<custom>), name
├─ description?, enabled, order, weight?
├─ consequenceScaleId           // ссылка на шкалу kind='consequence'
└─ descriptors: { scaleOrder, description }[]  // что значит каждый уровень тяжести
                                               // в этой категории

RiskMatrix                      // матрица под конкретный вид анализа
├─ id, code, name, description?
├─ analysisType: aca | fmeca | rcm | rbi | strategy
├─ probabilityScaleId           // ось вероятности (kind='probability')
├─ consequenceScaleId           // ось последствий (kind='consequence')
├─ rankMode: product | sum | explicit     // как считается риск-балл/ранг ячейки
├─ consequenceAggregation: max | weighted // как сводятся категории к оси
├─ isDefault                    // матрица по умолчанию для своего analysisType
├─ riskLevels: RiskLevel[]      // { code, name, tone, color?, order,
│                               //   scoreFrom, scoreTo, actionHint? } — зоны+пороги
└─ cells?: RiskMatrixCell[]     // только для rankMode='explicit':
                                //   { probabilityOrder, consequenceOrder, riskLevelCode }
```

Новые enum в `src/model/common.ts`: `riskAnalysisTypeSchema`,
`riskScaleKindSchema`, `consequenceCategoryCodeSchema`. Цвет зоны переиспользует
`statusToneSchema` (success/info/warning/error/default) + опциональный
произвольный `color` (hex) для случаев, когда нужно больше градаций, чем тонов.

```
01 модель+сиды ─┬─> 02 шкалы ─────────────┐
                ├─> 03 категории ──(нужны шкалы из 02)
                ├─> 04 уровни риска/зоны   │
                └─> 05 матрицы ◄───────────┴─ (связывают шкалы 02 + зоны 04)
                                   │

                                        замена жёстких порогов criticality.ts,
                                        миграция CriticalityAssessment)
```

## Согласованные решения (зафиксированы заказчиком 2026-06-08)

- **Навигация:** отдельный раздел **«Матрицы риска»** (конфигуратор) в sidebar
  рядом с «Анализ критичности»; «Анализ критичности» — его потребитель (вид
  анализа ACA).
- **Охват потребителей в этой итерации:** конфигуратор поддерживает все пять видов
  анализа (ACA/FMECA/RCM/RBI/стратегии), но **рабочим потребителем подключается
  только ACA** (анализ критичности). FMECA/RCM/RBI существуют как настраиваемые
  матрицы и сиды; их полноценные рабочие процессы — за рамками этой карты.
- **Цвет зоны:** по умолчанию — тоны брендбука; hex `color` — опциональное поле
  для расширенных палитр (5+ зон).

## Глобальные критерии готовности подсистемы

- [ ] Можно создать/отредактировать несколько матриц и назначить их видам анализа
      (ACA/FMECA/RCM/RBI/стратегии); у каждого вида есть матрица по умолчанию.
- [ ] Шкалы вероятности/последствий/критичности/ранга настраиваются (число уровней,
      подписи, описания, якоря) и переиспользуются матрицами.
- [ ] Категории последствий (производство/безопасность/экология/качество/финансы)
      настраиваются, описывают уровни тяжести и агрегируются на ось последствий.
- [ ] Уровни риска и цветовые зоны настраиваются порогами; матрица перекрашивается
      и валидирует непротиворечивость порогов.
- [ ] «Анализ критичности» работает поверх конфигурируемой матрицы ACA по
      умолчанию; жёсткие пороги из `services/criticality.ts` убраны.
- [ ] Старые `CriticalityAssessment` мигрируют без потерь; режимы хранения и сброс
      к сидам работают.
- [ ] `npm run lint` и `npm run build` проходят; документы актуализированы.

## Журнал решений

- 2026-06-08: подсистему ведём отдельной дорожной картой `risk-matrix-config/`
  (а не внутри завершённой `feature-buildout/`), т.к. это новый крупный
  функциональный блок поверх готового прототипа.
- 2026-06-08: дочерние коллекции конфигурации (уровни шкалы, уровни риска,
  описания категорий, явные ячейки) **встраиваем массивами в родительский
  документ**, а не делаем плоскими сущностями с `id` (как `Status`/`Transition`).
  Причина — конфигурация редактируется и валидируется как единый агрегат; это
  сокращает число датасетов и упрощает формы (RHF `useFieldArray`). Компромисс:
  меньше переиспользуемость отдельного уровня — приемлемо для конфигуратора.
- 2026-06-08: цвет зоны — `statusTone` по умолчанию + опциональный hex `color`,
  чтобы не плодить токены и при этом поддержать матрицы с 5+ зонами.
- 2026-06-08: в v1 единственный «потребитель» конфигурируемой матрицы — раздел
  «Анализ критичности» (вид анализа ACA). FMECA/RCM/RBI существуют как
  настраиваемые матрицы/сиды; их полноценные рабочие процессы — за рамками этой
  карты.
- 2026-06-08: заказчик подтвердил размещение **отдельным разделом «Матрицы риска»**
  и охват **только ACA** как рабочего потребителя в этой итерации.
