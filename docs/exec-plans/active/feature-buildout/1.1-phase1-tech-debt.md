# План: Реализация техдолга фазы 1

- Статус: active
- Фаза: **1.1** (между фазой 1 и фазой 2)
- Дата: 2026-06-04

## Цель

Закрыть компромиссы, накопленные при выполнении фазы 1 (поиск, справочники,
статусные схемы), **до** старта APM-надстройки (фаза 2). После фазы 1.1 модель
активов и справочников согласованы, статусы опираются на схему, а не на дублирующий
enum; фаза 2 не наследует расхождения данных.

## Контекст

- Источник долгов: [`../../tech-debt-tracker.md`](../../tech-debt-tracker.md)
  (записи от 2026-06-04) и журналы планов
  [`04-asset-search.md`](04-asset-search.md),
  [`05-catalogs.md`](05-catalogs.md),
  [`06-status-schemes.md`](06-status-schemes.md).
- Зависит от: фаза 1 (планы 04–06) — ✅ выполнена.
- Блокирует: фазу 2 (07–09) — желательно завершить 1.1 до критичности/стратегий,
  т.к. они тоже используют статусы и справочники.
- Не входит в 1.1 (отдельно или позже): drag&drop в классификаторе, полный CRUD
  значений атрибутов в карточке актива, миграция всех сущностей на статусные схемы
  (стратегии, обходы — в своих планах фазы 2+).

## Шаги

### TD-1. Статусы активов через статусную схему (влияние: сред)

- [ ] В модели `Asset`: заменить `status: assetStatusSchema` на ссылку на состояние
      схемы — `statusId: string` (или `currentStatusId`), опционально денормализованный
      `statusCode` для отображения/фильтров, если нужен для производительности.
- [ ] Обновить сиды активов: `statusId` → id из `statusSeed` схемы `ss-asset`
      (коды `in_operation`, `standby` и т.д. сохраняются в `Status.code`).
- [ ] Сервис `status-flow`: функция смены статуса актива с проверкой перехода
      (вызов из репозитория-обёртки или отдельного `assetStatusService`).
- [ ] Реестр: форма/карточка/таблица — бейджи и фильтры по `Status` из репозитория,
      не по `assetStatus` i18n-ключам enum.
- [ ] Поиск: фильтр «Статус» — по состояниям схемы актива (или по `statusId`).
- [ ] Удалить или пометить deprecated `assetStatusSchema` в `common.ts`; обновить
      все импорты.
- [ ] Миграция данных в localStorage/Dexie: при загрузке старых записей с полем
      `status` (enum) — маппинг code → `statusId` (одноразовый адаптер на границе
      хранилища).

### TD-2. Владелец и планировщик — ссылки на справочники (влияние: низк)

- [ ] В модели `Asset`: `ownerId` / `plannerId` (опционально, ссылка на `Person`),
      убрать или оставить устаревшие строковые поля только для миграции.
- [ ] Сиды: сопоставить строки «Иванов А. С.» и т.д. с `personSeed` по имени.
- [ ] Форма актива: выпадающие списки `Person` (фильтр по `orgUnit` при желании).
- [ ] Поиск: фильтры владелец/планировщик — из `persons`, не из distinct по строкам
      активов.
- [ ] Карточка актива (обзор): отображать ФИО из справочника.

### TD-3. Код-сплиттинг маршрутов (влияние: низ)

- [ ] `React.lazy` + `Suspense` для тяжёлых разделов в `router.tsx` (минимум:
      дашборд с Recharts, реестр с arborist/table — по факту замера).
- [ ] Проверить, что `pnpm build` не предупреждает о едином чанке > 500 kB
      (или снизить порог осознанно в `vite.config` с обоснованием в журнале).

- [ ] `owner`/`planner` активов — ссылки на `Person`; формы и поиск используют
      справочник.
- [ ] Сборка с lazy-маршрутами без предупреждения о монолитном чанке (или задокументировано исключение).
- [ ] Соответствующие записи в `tech-debt-tracker.md` переведены в `closed`.
- [ ] `pnpm lint` и `pnpm build` проходят.
- [ ] `ARCHITECTURE.md` и журнал дорожной карты обновлены.
