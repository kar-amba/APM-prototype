# Прототип APM ГлоуБайт — Продуктовое видение (v1)

> Статус: видение / черновик. Документ описывает целевой вид прототипа системы
> управления надёжностью активов. Прототип демонстрирует, как целевая система
> может выглядеть и работать на предприятии. Реальных интеграций нет — все
> внешние источники данных (телеметрия со станков, SCADA/IoT, ERP) **симулируются**.

---

## 1. Назначение и позиционирование

Прототип APM ГлоуБайт — это веб-приложение, которое **выглядит и ощущается как
промышленная система управления надёжностью активов** (класс EAM + APM), но при
этом не подключается к реальным системам предприятия. Вместо интеграций
используется предзаполненный набор данных «среднего предприятия» и встроенный
генератор «живых» показаний, который имитирует поступление данных с оборудования
и периодически выдаёт отклонения.

Цель — наглядно показать, как целевая система:
- ведёт иерархический реестр активов предприятия;
- хранит паспортные данные и атрибуты оборудования;
- позволяет искать и фильтровать активы;
- управляет жизненным циклом через настраиваемые статусные схемы;
- связывает активы со стратегиями обслуживания, мероприятиями, маршрутами и обходами.

### Класс системы
- **EAM (Enterprise Asset Management)** — учётный костяк: реестр, паспорта, статусы.
- **APM (Asset Performance Management)** — надстройка про надёжность: критичность,
  стратегии, мониторинг состояния, обходы, анализ отказов.

v1 реализует **ядро EAM с заделом под APM**.

## 2. Ключевые доменные принципы (из отраслевой практики)

Прототип опирается на устоявшиеся подходы реальных систем (IBM Maximo, GE Vernova
APM, AVEVA APM, 1С:ТОИР / 1С:RCM, Галактика EAM, ПО «Надёжность») и стандарт
**ISO 14224** (таксономия надёжности).

1. **Две связанные иерархии:**
   - **Функциональные места (Functional Locations)** — «где» выполняется функция:
     Предприятие → Цех → Участок → Технологическая позиция. Стабильный скелет,
     не меняется при замене железа.
   - **Оборудование (Assets)** — «что» физически установлено: Единица оборудования →
     Узел → Компонент. Может перемещаться между местами; перемещения фиксируются.

2. **Без «сирот»:** актив всегда привязан либо к функциональному месту, либо к
   родительскому активу, который привязан к месту.

3. **Принцип влияния:** отказ объекта нижнего уровня нарушает работу объекта выше
   по иерархии.

4. **Классификация и спецификации:** вместо сотен полей «на все случаи» — общий
   паспорт + классификатор (напр. Насос → Центробежный → Консольный), который
   подтягивает только релевантные атрибуты класса (для насоса — подача, напор,
   мощность; для двигателя — об/мин, фазность, напряжение). Это включает поиск по
   значениям атрибутов («все насосы с подачей ≥ 100 м³/ч»).

5. **Критичность → стратегия → мероприятия:** критичность (RCM/FMECA) ранжирует
   оборудование; на её основе назначается стратегия (реактивная → ППР → по
   состоянию → предиктивная), которая раскладывается в конкретные задачи с интервалами.

6. **Симулируемая «интеграция» через обходы:** замер вне допустимого диапазона на
   обходе автоматически порождает дефект/уведомление — это удобная и наглядная
   модель взаимодействия с «оборудованием» без реальной интеграции.

## 3. Роли пользователей

В v1 роли задают акценты интерфейса (без полноценной авторизации/прав):

- **Инженер по надёжности** — критичность, стратегии, анализ отказов.
- **Планировщик ТОиР** — реестр, мероприятия, назначение ответственных.
- **Оператор** — выполнение обходов с мобильно-подобного экрана.
- **Руководитель** — дашборд и KPI надёжности.

---

## 4. Карта разделов (информационная архитектура)

1. **Дашборд надёжности** — KPI-плитки, топ критичных активов, последние отклонения
   по обходам, открытые дефекты, выполнение обходов.
2. **Реестр активов** — ядро: дерево иерархии + таблица + карточка актива.
3. **Поиск активов** — расширенный фильтр и сохраняемые представления.
4. **Стратегии и мероприятия** — стратегии обслуживания, привязка к активам/классам,
   задачи с интервалами.
5. **Обходы и маршруты** — конструктор маршрутов, экран выполнения обхода, журнал замеров.
6. **Анализ критичности** — матрица критичности (последствия × вероятность).
7. **Конфигуратор статусных схем** — состояния и переходы, переиспользуемые для
   активов, анализов, стратегий, мероприятий, маршрутов.
8. **Справочники** — классификаторы, цеха/участки, производители, единицы измерения, персонал.

## 5. Ключевой UX-паттерн рабочего пространства

Сквозной паттерн — **«дерево + список + детали» (three-pane)**:

- **Слева:** дерево иерархии (функциональные места / оборудование) с поиском по дереву.
- **По центру:** плотная таблица активов выбранной ветки — сортировка, фильтры,
  колонки статуса и критичности.
- **Справа / отдельный экран:** карточка актива с вкладками.

### Карточка актива (вкладки)
- **Обзор** — ключевые поля, статус, критичность, текущие показания.
- **Паспорт и атрибуты** — паспортные данные + динамические атрибуты класса.
- **Иерархия** — место установки, родитель, дочерние узлы/компоненты, перемещения.
- **Стратегия и мероприятия** — назначенная стратегия и задачи ТОиР.
- **Обходы и замеры** — точки контроля, история замеров, отклонения.
- **История и отказы** — дефекты, события, изменения статуса.
- **Документы** — паспорта (PDF), фото, схемы.

### Поиск активов (атрибуты фильтра)
Идентификатор / номенклатура, инв./зав./технол. номер, класс, цех, участок,
функциональное место, владелец, ответственный планировщик, статус, критичность,
производитель/модель, **значения атрибутов классификации**.

---

## 6. Модель данных (v1)

- **FunctionalLocation** — id, код, название, родитель, тип уровня (предприятие/цех/
  участок/тех. позиция).
- **Asset** — id, инв./зав./технол. номера, наименование, классификатор,
  функциональное место, родительский актив, производитель, модель, серийный номер,
  дата ввода в эксплуатацию, статус, критичность, владелец, ответственный
  планировщик, стоимость замещения.
- **Classification / Attribute / AssetAttributeValue** — динамические атрибуты по классу.
- **StatusScheme / Status / Transition** — настраиваемые статусные модели (для разных сущностей).
- **Strategy → MaintenanceTask** — стратегия и задачи (интервал, тип: ППР / по состоянию).
- **Route → RoutePoint → MeasurementPoint/ChecklistItem** — маршруты и точки контроля
  с допустимыми диапазонами; **RoundExecution → Reading** — выполнение и замеры.
- **CriticalityAssessment** — оценка критичности.
- **Defect / Notification** — порождается из отклонений на обходах.
- **Document, Manufacturer, OrgUnit (цех/участок), Person**.

## 7. Демо-предприятие для предзаполнения

**Металлургический / обогатительный комбинат «ГлоуБайт-Металл»** — среднего размера,
правдоподобной структуры:

- **Цеха:** Дробильно-обогатительный, Плавильно-печной, Прокатный, Энергетический
  (компрессорная / насосная станции).
- **Участки:** ~10–15 (дробление, грохочение, измельчение, флотация, плавка, прокат,
  энергоснабжение и т.д.).
- **Оборудование:** ~150–300 единиц — дробилки, грохоты, конвейеры, мельницы,
  флотомашины, плавильные/нагревательные печи, насосы, компрессоры, мостовые краны,
  вентиляционные установки; у каждого — узлы и ключевые компоненты.
- **Предзаполнение:** паспорта, классы с атрибутами, статусы, критичность,
  3–5 маршрутов обхода с историей замеров и несколькими «сработавшими» отклонениями.

Цель — чтобы при первом открытии система выглядела «живой» и наполненной.

## 8. Визуальный язык

Прототип строится на дизайн-системе из `docs/brandbook-template.html`:
светлая деловая тема, шрифты Inter / JetBrains Mono, базовая плотность 14px,
готовые компоненты (таблицы, бейджи, карточки, метрики, табы, статусные цвета).
Это обеспечивает узнаваемый вид «продукта ГлоуБайт» из коробки.

## 9. Технологический подход (предварительно)

Так как реальных интеграций нет, оптимален **фронтенд-ориентированный SPA с
локальными данными**:
- React + TypeScript + Vite;
- данные через JSON-сиды + тонкий слой «API-симулятора»;
- «телеметрия оборудования» — генератор показаний во времени в браузере;
- без обязательного бэкенда → быстрый старт и полностью офлайн-демо.

Детальный стек фиксируется отдельно в `docs/techstack/main.md`.

## 10. Охват v1 и за его пределами

**Входит в v1 (полный заявленный объём):**
- Иерархический реестр активов (функциональные системы, единицы оборудования, узлы, компоненты).
- Карточка актива с паспортными данными, атрибутами, местом установки, производителем,
  моделью, серийным номером.
- Поиск активов по номенклатуре, идентификатору, цеху, участку, владельцу,
  ответственному планировщику и иным атрибутам.
- Настройка статусных схем (для анализов, стратегий, мероприятий, маршрутов, обходов и пр.).
- Стратегии и мероприятия, маршруты и обходы, анализ критичности.
- Предзаполненное демо-предприятие.

**Вне рамок v1 (следующие версии):**
- Реальные интеграции (SCADA/IoT/ERP).
- Полноценная авторизация и ролевая модель прав.
- Планирование ресурсов и наряды, склад запчастей.
- Нативное мобильное приложение.
- Предиктивная аналитика на ML.
